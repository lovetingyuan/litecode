## 问题详情

### 1. [P1] 单独打开文件时，可以绕过执行信任检查

**功能背景与触发条件**

终端、语言服务和外部格式化器通过工作区信任限制项目代码执行。问题发生在窗口没有打开工作区、只打开一个松散文件时：窗口的 root 为空，但文件所在目录可能包含来自不可信来源的工具脚本。

触发需要 Node.js 可用，且格式化逻辑选中了该目录中的项目工具。用户主动格式化，或启用了保存时格式化，都可能进入这条路径。并非仅打开任意文本文件就一定执行外部脚本。

**复现步骤**

1. 在独立测试目录准备一个 HTML 或 TypeScript 文件。
2. 在该目录准备 node_modules/prettier/bin/prettier.cjs。
3. 使用没有打开工作区的新窗口，仅打开这个文件，不授予其目录执行信任。
4. 执行格式化；也可在启用保存时格式化后触发保存。

安全的桌面补验可以让测试脚本仅向标准错误输出 AUDIT_FORMATTER_EXECUTED 并以非零状态退出，以错误提示确认执行路径。不要用真实有害脚本验证。

**预期与实际**

预期：未经执行信任授权的目录，不能自动成为外部项目工具的来源。

实际：require_workspace_trust() 在 root 为空时返回 Ok(None)。format_document() 随后把文件父目录作为执行目录，并优先选择其中的 Prettier 脚本；前端没有收到工作区信任拒绝，自然也不会弹出对应授权提示。

**根因与源码定位**

- [src-tauri/src/state.rs:140](../../src-tauri/src/state.rs#L140)：只有 root 存在时才检查是否受信任。
- [src-tauri/src/tools.rs:320](../../src-tauri/src/tools.rs#L320)：没有工作区时回退到文件父目录。
- [src-tauri/src/tools.rs:337](../../src-tauri/src/tools.rs#L337)：选择该目录中的项目 Prettier。
- [src-tauri/src/tools.rs:389](../../src-tauri/src/tools.rs#L389)：通过 Node.js 执行脚本。

**用户影响**

不可信目录中的脚本可以获得当前用户权限下的代码执行机会。格式化和保存不应隐式扩大文件目录的执行信任。

**最小修复建议**

在格式化执行边界验证实际项目工具及其配置来源的信任；松散文件的目录不能因 root 为空而自动放行。未经授权时，停止选择该目录中的项目工具，并提供明确的授权入口。

不要简单把所有 root 为空的执行请求一律拒绝，否则会连带改变空窗口终端等已有行为。应先修复会从文件目录发现并执行项目代码的具体路径。

**建议补充的回归测试**

- 未授信松散文件目录中的测试格式化脚本不能被启动。
- 保存时格式化遵守相同边界。
- 明确授权后才能执行，拒绝授权时仍能编辑文本。
- 已信任工作区中打开工作区外的文件时，检查实际工具与配置来源，避免以无关根目录的信任覆盖其他目录。

**证据与限制**

实际状态函数检查得到“loose-file window: Ok(None)”，执行目标由上述代码链路确认。本次没有在桌面应用中执行测试格式化脚本，也没有执行有害脚本。

**第三轮修复进展（2026-10-26）**

- [formatter_trust.rs](../../src-tauri/src/formatter_trust.rs) 为格式化增加独立的来源授权。松散文件目录、工作区外文件、项目工具的真实规范化位置，以及工作区外配置均需明确授权；目录联接不会继承其表面路径所属工作区的信任。空窗口终端的既有信任策略不变。
- [tools.rs](../../src-tauri/src/tools.rs) 在选择工具前检查文件目录，在启动进程的磁盘锁内重新检查工作区及全部来源。Prettier、Oxfmt 和 Rustfmt 显式使用已检查的配置；没有配置时使用禁用配置或临时空配置，避免重新自动发现未经检查的祖先配置。Rustup 的工作目录工具链文件也纳入检查。
- 前端遇到 formatterTrust 时显示实际待授权目录；只有点击 Trust Formatters 才调用原生 trust_formatter 并重试。并发请求共享提示，不重复重试同一拒绝；取消或切换工作区后不继续。授权仅保存在当前原生窗口内，按工作区上下文隔离，不写入永久工作区信任；撤销当前工作区信任会清除该窗口的格式化授权。
- 保存时格式化复用同一授权边界。用户取消时不执行项目脚本，仍保存当前文本；明确授权目录意味着允许该目录中的格式化代码以当前用户权限执行，并非对其进行沙箱隔离。
- 永久回归与真实桌面补验见第三轮验证记录；原始失败证据保留在上文，不代表修复后的行为。

### 2. [P1] 移动文件可能丢失源文档的未保存修改

**功能背景与触发条件**

移动或重命名文件后，编辑器需要把源文档重新绑定到新的 Monaco URI。磁盘目标不存在，不代表编辑器中没有该目标的文本模型：文件被外部删除后，其含有未保存内容的标签页仍可能保留。

**复现步骤**

1. 打开源文件 a.txt，写入未保存内容 SOURCE UNSAVED IMPORTANT。
2. 打开目标路径 sub/a.txt，保留另一份未保存内容 TARGET UNSAVED IMPORTANT。
3. 从磁盘删除目标文件，但保留其编辑标签页。
4. 将源文件移动到 sub/a.txt；对应隔离用例直接调用移动后的 renameDocuments() 绑定逻辑。

**预期与实际**

预期：操作应在冲突检查阶段被拒绝，或显式处理两个编辑文档；两份未保存内容均应保留。

实际：attachDocument() 查到目标 URI 已有模型后直接复用，不使用传入的源文本。rebindDocument() 随后销毁源模型。隔离用例中，源文档内容变成目标内容，两个文档共享同一个模型。

    source content after move: TARGET UNSAVED IMPORTANT
    models shared: true

核心断言为“移动后源模型内容仍应等于 SOURCE UNSAVED IMPORTANT”；当前实现未通过。

**根因与源码定位**

- [src/editor/documents.ts:215](../../src/editor/documents.ts#L215)：目标 URI 存在时直接使用既有模型。
- [src/editor/documents.ts:1245](../../src/editor/documents.ts#L1245)：移动后逐个重新绑定文档。
- [src/editor/documents.ts:1290](../../src/editor/documents.ts#L1290)：重新附加源文档。
- [src/editor/documents.ts:1304](../../src/editor/documents.ts#L1304)：销毁旧源模型。

**用户影响**

源文档的未保存内容会从活动模型中消失；后续备份还可能将错误绑定后的内容写入恢复记录。不能依赖磁盘上仍有已保存版本来保护尚未保存的修改。

**最小修复建议**

在磁盘移动前，检查所有目标路径是否被其他打开文档占用，包括已从磁盘删除的文档。发现冲突时整批拒绝，并保留当前编辑状态。

重新绑定函数也应防御性检查目标模型的归属，不能静默接管另一文档的模型。目录移动需要检查全部受影响的后代目标。

**建议补充的回归测试**

- 源和已删除目标均含未保存修改时，拒绝移动且两份内容不变。
- 目录移动中的一个后代存在上述冲突时，不发生部分模型接管。
- 正常移动后，源文本、dirty 标记和保存目的地保持正确。
- 不同文档不会因重新绑定意外共享同一个文本模型。

**证据与限制**

使用项目实际 renameDocuments()、rebindDocument() 和 attachDocument()，通过按 URI 保存模型的测试注册表复现。未执行完整原生磁盘移动；磁盘目标已不存在是本用例的前置条件。

**修复进展（2026-10-26）**

- [documents.ts](../../src/editor/documents.ts) 的移动协调器现在接收完整的来源与目标映射；排空旧保存、旧备份后，预检整批目标及目录后代。其他打开文档（包括已删除文档）占用目标时，在磁盘操作前拒绝整批移动。
- 重新绑定前再检查整批目标，attachDocument() 和 rebindDocument() 均防止接管其他模型。目标 URI 仍对应源模型时只更新路径，保留模型和 dirty 状态。
- 移动期间等待相关文件打开；读取横跨移动时丢弃结果并重新读取，防止旧文本在移动完成后重新占用 URI。
- 永久测试使用按 URI 注册、查询和销毁的模型，覆盖双 dirty 文档、目录后代冲突、过时读取、正常移动与大小写重命名。

### 3. [P1] 文件移动期间关闭窗口，会漏掉最后的恢复备份

**功能背景与触发条件**

beginDocumentMove() 暂停新备份，避免移动过程中持久化过时路径。暂停本身有合理目的，但窗口关闭流程没有区分“备份已完成”和“备份因移动而被跳过”。

移动状态在等待既有保存和备份排空前就已设置，因此触发窗口并不限于实际文件重命名的短暂瞬间。

**复现步骤**

1. 为一个打开文档完成一次 checkpoint()。
2. 调用 beginDocumentMove()，保持移动状态未释放。
3. 将文档改为 last important edit before closing。
4. 走关闭流程中的 checkpoint()，检查最后发送的恢复快照。

**预期与实际**

预期：关闭操作等待移动与保存协调完成，把最新内容和最终路径写入恢复快照；失败时保留窗口。

实际：checkpoint() 在 documentMove 非空时直接返回。关闭回调随后执行窗口销毁。隔离用例显示最新内容没有进入最后一次快照：

    audit backup at close: edited
    live: last important edit before closing

**根因与源码定位**

- [src/editor/documents.ts:45](../../src/editor/documents.ts#L45)：建立移动状态并等待已有操作。
- [src/editor/documents.ts:175](../../src/editor/documents.ts#L175)：移动期间跳过 checkpoint()。
- [src/components/App.tsx:201](../../src/components/App.tsx#L201)：等待 checkpoint() 返回后直接销毁窗口。
- [src/editor/documents.test.ts:1094](../../src/editor/documents.test.ts#L1094)：原有测试验证移动期间延迟备份，但没有验证关闭所需的持久化保证。

**用户影响**

窗口正常关闭也可能丢失最后的未保存修改，恢复机制只能读到较早快照。后端销毁时再持久化已有镜像，不能补回从未同步过来的前端最新文本。

**最小修复建议**

让关闭流程等待移动屏障及相关保存完成，再生成并确认一次最新快照。不能把被跳过的周期备份当作关闭前的成功落盘确认。

协调顺序需要避免移动流程等待旧备份、旧备份又等待该移动完成的循环等待。

**建议补充的回归测试**

- 移动等待旧保存时关闭窗口，销毁前必须持久化最后编辑。
- 移动完成后，恢复快照使用新路径和最新文本。
- 移动或最终备份失败时，不销毁窗口并显示错误。
- 原有“移动期间不写入旧路径快照”的约束继续成立。

**证据与限制**

隔离测试复现了最新文本未进入快照；窗口最终销毁及后端镜像行为通过调用链确认。本次没有进行真实窗口关闭后的完整桌面重启验收。

**修复进展（2026-10-26）**

- 关闭入口改用 closeWindowWithRecovery()，合并重复关闭请求，并通过 checkpoint({ waitForMoves: true }) 等待移动及保存完成，再捕获最新快照。
- 等待移动的步骤位于备份队列之外，周期备份仍在移动期间延期，避免移动排空旧备份时产生循环等待。最终快照确认期间若又出现编辑、保存或移动，会重新检查并补做快照。

- 永久测试验证新路径和最后文本、确认前不销毁、重复关闭只销毁一次、移动失败和备份失败后保留窗口，以及最终快照期间又发生移动的情况。

### 5. [P1] 大量匹配的替换规划会长时间阻塞窗口

**功能背景与触发条件**

工作区替换先计算每个匹配的编辑范围和替换文本。当前允许最多 20,000 处匹配，搜索接受的文件大小范围也足以容纳本次基准输入。

问题并不需要超大文件：当匹配分布在文本各处时，重复的位置计算会随匹配数量快速放大。

**复现步骤**

1. 每行构造“needle + 506 个 x + 换行”，每行 513 字节。
2. 分别生成 1,000、4,000 和 16,000 行。
3. 执行区分大小写、非正则、非整词的 needle 到 new 的替换规划。
4. 单独计时实际 replacement::plan() 调用，不包含 UI、IPC 和磁盘事务。

**预期与实际**

预期：位置计算随文本长度和匹配数近似线性增长，计算期间窗口仍可响应。

实际：每个匹配起点和终点都重新调用 byte_position()；该函数从文本开头重新计算行号。实测如下：

| 匹配数 | 文本字节数 | 约合大小 | 单次调用耗时 |
| ---: | ---: | ---: | ---: |
| 1,000 | 513,000 | 0.49 MiB | 320 ms |
| 4,000 | 2,052,000 | 1.96 MiB | 5,071 ms |
| 16,000 | 8,208,000 | 7.83 MiB | 81,185 ms |

本组输入中，匹配数和文件长度同时扩大 4 倍，耗时约扩大 16 倍。此前报告中的“约 2 MiB／5 秒”和“约 8 MiB／81 秒”是上述数据的四舍五入描述。

**根因与源码定位**

- [src-tauri/src/search.rs:144](../../src-tauri/src/search.rs#L144)：byte_position() 重复扫描起点之前的文本。
- [src-tauri/src/replacement.rs:170](../../src-tauri/src/replacement.rs#L170)：每个匹配进行两次位置计算。
- [src-tauri/src/replacement.rs:187](../../src-tauri/src/replacement.rs#L187)：replacement_plan 是同步 Tauri 命令，直接调用计算函数。

**用户影响**

在合法输入范围内，替换预览或执行前的规划即可持续数十秒。同步命令入口会阻塞窗口线程；本次没有测量真实窗口冻结时长，81,185 ms 是算法单独调用的耗时。

**最小修复建议**

按匹配偏移单调递增的顺序维护当前字节位置、行和 UTF-16 列，避免从头扫描；将耗时计算移到后台，并支持取消。仅移到后台可以缓解窗口阻塞，但不能解决计算量本身。

**建议补充的回归测试**

- 保留中文、emoji、CRLF、多行匹配等位置正确性测试。
- 对分散匹配的大文本设置独立性能基准，比较扩大输入后的增长趋势。
- 取消大型规划后及时返回，窗口在规划期间仍能交互。
- 不把本机绝对毫秒数直接作为普通 CI 的固定阈值。

**证据与限制**

使用基准提交中的实际替换算法和 byte_position()，独立 Rust 探针以 -O 编译主模块，链接当前已有的 debug 依赖；仅移除 Tauri 命令属性并提供探针所需的类型环境。算法没有重新实现。

这不是完整 Release 应用的端到端计时，也没有包含全部前端规划开销。主机与运行方式见后文验证记录。

**第二轮修复进展（2026-10-26）**

- [replacement.rs](../../src-tauri/src/replacement.rs) 使用位置游标累计行和 UTF-16 列，并通过异步命令及 spawn_blocking 执行。额外定位到 PCRE2 解释器在迭代时重复校验剩余 UTF 输入；启用现有 JIT 支持后，审计输入的增长接近线性。JIT 匹配失败时退回原解释器，保留长匹配等正则兼容性。
- 增加按窗口隔离的 replacement_plan_begin、replacement_plan_cancel、replacement_plan_release；规划调用携带 requestId。注册确认后才计算，取消发生在注册响应之前时也不启动计算；关闭或重载窗口取消并释放遗留任务。
- 前端分组采用原地追加、规划范围索引和排序后的文本片段合并，每批检查取消并按时间预算让出事件循环。保留搜索范围、模型版本、原始磁盘 revision 与提交前检查。
- 搜索面板增加规划状态和取消按钮；取消、查询变化、清空结果或工作区切换会丢弃整批规划。replaceMatches() 取消时返回 null，界面据此避免自动重跑搜索。提交事务前再次检查，进入写入阶段后不再接受规划取消，原有事务格式与恢复保证不变。
- 取消属于协作检查，不能抢占正在执行的单次 PCRE2 调用。JIT 不可用或特殊模式回退解释器时仍保留其执行成本；不声称任意正则均有线性复杂度。具体基准和桌面交互验证见第二轮验证记录。

### 8. [P2] 批量替换反复重写完整快照，磁盘写入量过大

**功能背景与触发条件**

**用户影响**

将不可变内容快照与小型可变进度分开保存；快照只写一次，进度更新保留原有的持久化确认顺序。不要通过降低原有恢复保证或直接删除备份来换取速度。

**建议补充的回归测试**

- 继续通过写入前后、进度落盘前后中断和恢复的现有测试。
- 使用记录写入字节数的存储替身或独立基准，确认进度写入不再重复携带整批文本。
- 部分失败、重试、撤销、重做均保留原始字节和外部修改检查。
- 大批次执行期间，取消与其他文档保存的等待行为可验证。

**证据与限制**

持久化调用链已确认；15.512 GiB 是序列化体积乘以更新次数的推算，不是磁盘实测，不代表已经测得同等 SSD 物理写入量或操作耗时。可复现计算见后文。

### 9. [P2] GBK 文本被当作二进制文件，无法正常编辑

**功能背景与触发条件**

底层 files 模块支持显式 GBK 解码，但文件打开前会先进行媒体或文本分类。没有 UTF-16 BOM 且样本不是合法 UTF-8 的普通中文文件，会提前被分到二进制分支。

**复现步骤**

1. 使用 files::encode("中文内容", "gbk") 生成普通文本文件。
2. 调用 media::inspect()，检查分类。
3. 调用 files::read() 并显式指定 GBK，检查文本是否能够正确读取。
4. 通过正常打开入口检查它是否建立文本模型。

**预期与实际**

预期：无法按 UTF-8 解码时，用户可以选择 GBK 重新打开，保留原始字节并进入文本编辑。

实际函数结果：

    bytes: d6 d0 ce c4 c4 da c8 dd
    media::inspect kind: Binary
    files::read with GBK: "中文内容"

openPath() 仅为 text 或 svg 调用文本读取，因此后端已有的 GBK 能力没有进入正常打开流程。现有编码选择只修改文档编码信息，不提供按编码重读文件的完整流程。

**根因与源码定位**

- [src-tauri/src/media.rs:77](../../src-tauri/src/media.rs#L77)：非法 UTF-8 样本参与二进制判定。
- [src/editor/documents.ts:322](../../src/editor/documents.ts#L322)：二进制分类跳过 read_document。
- [src-tauri/src/files.rs:24](../../src-tauri/src/files.rs#L24)：实际支持 GBK 解码。
- [src/editor/editorStatus.ts:32](../../src/editor/editorStatus.ts#L32)：编码选择流程。

**用户影响**

合法的中文源文件、配置和旧项目文本显示为不可编辑的二进制预览。用户无法通过现有正常打开入口使用底层已经具备的解码功能。

**最小修复建议**

区分“已确认二进制格式”和“无法按 UTF-8 解码”。后一种情况提供显式按 GBK、UTF-16 等编码重新读取的入口，不在确认前替换原始字节。

**建议补充的回归测试**

- GBK 中文文件可按指定编码重开，未修改时不写入磁盘。
- 读取失败时不把替换字符作为正常文本保存。
- UTF-8、带 BOM 的 UTF-8、UTF-16 原有打开行为继续正确。
- 已确认二进制文件仍保持预览或拒绝文本读取。

**证据与限制**

分类和指定编码读取使用实际 Rust 函数实测；前端跳过读取的后果由代码链路确认。没有完成原生文件选择器到编码重开的桌面验收。

### 10. [P2] 网络共享路径转换错误，影响文件和工作区打开

**功能背景与触发条件**

**复现步骤**

1. 取输入路径 \\?\UNC\server\share\project。
2. 按 commands::visible_path() 当前逻辑删除 \\?\ 前缀。
3. 将结果作为文件或工作区路径继续传递。

**预期与实际**

    输入：\\?\UNC\server\share\project
    预期：\\server\share\project
    实际：UNC\server\share\project

实际结果失去网络路径前缀，成为错误的相对路径。该函数用于文件选择、工作区和恢复数据等路径返回过程，会影响后续授权、目录读取和文件打开。

**根因与源码定位**

- [src-tauri/src/tools.rs:20](../../src-tauri/src/tools.rs#L20)：进程边界也已有正确的 UNC 转换逻辑。

**用户影响**

**最小修复建议**
